# Исследовательский прогон

Цель — получить проверяемые цифры о поведении агента, а не красивую историю. Любое заявление в отчёте или питче должно указывать на файл с прогоном, откуда оно взято.

## 1. Выбрать стенд и записать, что это за стенд

| Стенд | Когда | Ограничение, которое обязательно указать |
| --- | --- | --- |
| Подменная среда (`backend/tests/fakes.py`) через `scripts/analysis/*.py` | Проверка алгоритмов, сравнение настроек, калибровка | Не Gazebo: нет физики, модель сигнала и грунтов — допущения |
| Офлайн-стенд `scripts/analysis/offline_stand.py` + frontend | Проверка панели, HTTP и экспорта вживую | То же, что выше; LLM только если заданы `LLM_*` |
| Стенд A (Gazebo + судья) | Физическое подтверждение, рубежи | Стенд принадлежит A; B его не запускает |

Запуск офлайн-стенда и панели:

```bash
PYTHONPATH=backend/src:backend/tests:scripts/analysis backend/.venv/bin/python scripts/analysis/offline_stand.py
cd frontend && BACKEND_URL=http://localhost:8010 npx vite --port 8090
```

## 2. Зафиксировать протокол до запуска

Запиши в журнал процесса (`context/full-solution/reports/b-process.md`): commit, профили, seed, режим карты, число роботов, планировщик (LLM/резерв), какие пороги сравниваются. Пороги и контрольный набор не меняются после того, как ты увидел результат на этом наборе: иначе цифры подгоняются под ответ. Если менять пришлось — запиши причину и прогони заново.

## 3. Прогнать серию со всеми исходами

Готовые серии:

- `scripts/analysis/offline_series.py N` — easy/medium/hard × N seed, полная выгрузка `<run_id>/{journal.jsonl,state.json,manifest.json,truth.json}`;
- `search_limits.py`, `adaptation.py`, `slam_runs.py`, `team_runs.py` — сравнения конкретных решений.

Не удаляй неудачные прогоны и не сокращай серию до удачных seed. `truth.json` — закрытое расписание подменной среды: его читает только оценщик после прогона, в агент и промпт оно не попадает.

## 4. Посчитать метрики

```bash
python3 scripts/analysis/metrics.py artifacts/analysis/offline-series --out artifacts/analysis/metrics-<имя>.json
```

Скрипт принимает каталоги прогонов, `run-N.json` приёмки MVP и экспорт панели. Смотри в сводке: возвраты, распределение сборов (не только среднее), ложные сборы, исходы гипотез, обнаружения, перепланирования, долю планов LLM, ошибку прогноза расхода маршрута (положительная — прогноз консервативен).

## 5. Проверить научную цепочку

```bash
python3 .agents/skills/research-run/scripts/check_science_chain.py <journal.jsonl или каталог прогона>
```

Для каждой гипотезы скрипт показывает: прогноз записан до проверки, был ли проверочный эксперимент, есть ли независимое измерение, вывод и запись «Вывод учтён в решении». Вывод без измерения или прогноз после эксперимента — дефект, а не стилистика.

## 6. Сверить обнаружения с расписанием

Изменение засчитывается как пропущенное только если оно было наблюдаемо: для грунта — контакт с зоной и до, и после изменения; для опасности — событие `hazard_hit`. Изменение в непосещённой области не пропуск. Обнаружение без изменения — ложная тревога, даже если затем проверочная гипотеза его опровергла (это стоит отметить отдельно как самоисправление).

## 7. Записать результат

Формат записи в отчёт или `artifacts/analysis/<тема>.md`:

```markdown
# <Что проверяли>
**Стенд:** ... (и что он не доказывает)
**Команда:** ...   **Commit:** ...   **Прогоны:** <путь к JSON>
| Конфигурация | runs | вернулись | сборы (среднее/медиана/мин–макс) | ложные сборы | ... |
**Вывод:** что подтверждено, что нет; цели проекта, которые не достигнуты, названы прямо.
```

Если улучшение мало или разнонаправлено по seed, так и пиши: «преимущество не доказано». Цифры подменной среды не выдаются за Gazebo, а локальный судья — за официального.

Пример применения на реальной серии — `examples/2026-10-07-offline-series.md`.
