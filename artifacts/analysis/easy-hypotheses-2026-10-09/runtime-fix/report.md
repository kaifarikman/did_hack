# Диагностика планировщика и наблюдений · 2026-10-09

Пробы выполнены в работающем `did-defense-backend-1`, без запуска/reset миссии и без команд движения. Model/endpoint/ключ не менялись. Секреты и тела ответов провайдера не записывались.

## LLM

- Единственная попытка обычного planner payload с runtime timeout 8 с завершилась сетевым таймаутом за **8,259 с**.
- Дополнительная диагностическая попытка того же payload с 30 с завершилась таймаутом за **30,512 с**. Production deadline не увеличивали.
- Уточняющий минимальный запрос «Reply OK.» к тому же endpoint/model получил ответ за **14,356 с**, 19 входных / 5 выходных токенов. Proxy не настроен, маршрут endpoint соответствует `/chat/completions`. Следовательно сервис способен отвечать, но даже минимальный ответ медленнее бюджета робота; причина задержки сложного planner payload остаётся не установлена.
- Отдельная проба соединения без запроса модели: DNS **0,003 с**, TCP **0,230 с**, TLS **0,453 с**. Доступность хоста подтверждена; полноценный planner-ответ не получен. Причина на стороне сервиса/ответа после установления соединения не установлена.
- В исходном коде две попытки по 8 с конфликтовали с deadline исполнителя 10 с. Истечение deadline лишь удаляло ссылку на Future, не отменяло retry и не снимало очередь. Два регрессионных теста до исправления падали.

Исправлено:

1. `LLM_TIMEOUT_S` теперь общий бюджет попыток одного плана; следующая попытка получает только остаток времени. После отмены ответ не принимается.
2. Stop/deadline передаёт отдельный cancellation token запросу и отменяет ещё не начатый Future. Пока прежний worker ещё занят, используется немедленный fallback; очередь устаревших запросов не накапливается.
3. После двух неудачных запросов сеть не вызывается 30 с; затем допускается recovery probe. Успех закрывает circuit, очередной сбой снова открывает. Новый controller начинает с закрытого circuit.
4. Конфигурация с LLM_TIMEOUT_S ≥ дедлайна исполнителя отклоняется при запуске, чтобы исключить противоречивые бюджеты.
5. Причина fallback сохраняется в журнале; сетевой сбой и deadline исполнителя не смешиваются.

`backend/.venv/bin/python -m pytest -q backend/tests/test_llm.py backend/tests/test_planner_lifecycle.py`: **51 passed**. Включает отмену, остаток бюджета, очередь, recovery и валидацию конфигурации. Ранее объединённый адресный набор с `test_controller.py`: **79 passed** до добавления последних двух lifecycle тестов. Compose config и compose-only leak check прошли.

Ограничение: urllib socket timeout ограничивает ожидание ввода/вывода, но не принудительно прерывает Python thread при потоке медленных частичных байтов. В таком случае deadline исполнителя по-прежнему запускает fallback, новый запрос не ставится за зависшим worker. Это не объявляется восстановлением внешнего сервиса.

## ROS

В старом failed snapshot odom/scan/battery устарели примерно на 14,9 с, но clock оставался свежим (0,016 с). Текущая приёмка recovered: 10-секундный read-only subscriber получил clock8785, odom457, scan45, telemetry50; максимальный перерыв 0,373 с, разница stamp относительно clock ≤0,049 с. Порог безопасности не изменён.

Обнаружен отдельный воспроизводимый расход CPU: все callbacks ROS bridge находятся в одном стандартном MutuallyExclusive callback group, но runtime использует четыре executor workers. `observation_probe.py` воспроизводит одинаковые четыре подписки; запуск без аргументов — SingleThreaded, с `multi` — MultiThreaded(4).

| Executor | CPU за 10 с | clock callbacks | odom | scan | telemetry |
|---|---:|---:|---:|---:|---:|
| MultiThreaded(4) | 8,732 с | 3199 | 369 | 37 | 49 |
| SingleThreaded | 2,042 с | 8584 | 452 | 44 | 50 |

Это свидетельство лишнего CPU и задержек обслуживания очереди в существующем режиме. Само по себе оно **не доказывает причину исторической остановки observations_stale**. Порог не повышается, fail-safe остаётся активным; финальный повтор миссии выполняет владелец стенда.

После согласования runtime переведён на SingleThreadedExecutor. Асинхронные вызовы судьи не блокируют callbacks; legacy blocking collect/finish вызываются вне executor. К ROS observation добавлен стабильный timestamp получения сигнала для научного цикла. В контейнере в отдельном ROS_DOMAIN_ID=83 прошли **20 тестов** `test_ros_generation.py` + `test_ros_runtime.py`, включая настоящий service exchange и неизменность sensor identity между чтениями. Живой основной стек не перезапускался этим агентом.
