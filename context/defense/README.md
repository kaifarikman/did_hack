# Подготовка защиты: три независимых задания

Дата: 2026-10-08. Пользователь поручил подготовить задания для трёх исполнителей. Это отдельный поток подготовки показа; полный пул T01–T36 сохраняется и не объявляется завершённым.

## Запуск работы

Каждому исполнителю передать один файл:

1. [Агент 1 — backend пользовательской цели](agent-1-navigation.md).
2. [Агент 2 — интерфейс задания точки](agent-2-interface.md).
3. [Агент 3 — доказательства, презентация и демо](agent-3-defense.md).

Все читают [общий контракт](contract.md) и [полученные требования](requirements.md). Задания подготовлены; новые исполнители этим документом не запущены.

## Разделение файлов

| Исполнитель | Исключительное владение | Работа независимо |
| --- | --- | --- |
| 1 | `backend/`, `context/defense/reports/agent-1.md` | Проверяет application и HTTP на fake-портах; использует общий контракт |
| 2 | `frontend/`, `context/defense/reports/agent-2.md` | Реализует тот же контракт через fixture gateway; не ждёт backend |
| 3 | `presentation/`, `scripts/defense/`, `artifacts/defense/`, `context/defense/reports/agent-3.md` | Готовит материалы и испытательный сценарий на существующих свидетельствах; финальный live проходит после объединения 1+2 |

`simulation/`, Compose, общий контекст и существующие исходные fixtures в `context/mvp/examples/` не редактировать параллельно. Новый контракт этого потока уже описан ниже; его несовместимое изменение требует синхронного обновления заданий обоих исполнителей интегратором. Новые fixtures агент 1 хранит в backend/tests, агент 2 — в frontend; один не запускает sync-скрипт поверх файлов другого.

Перед созданием worktree интегратор сохраняет актуальную общую основу: текущий `main` содержит незакоммиченные изменения T01–T12, чистый checkout старого HEAD их не получит. Не начинать с устаревшего main и не переносить только часть зависимых ROS/HTTP-правок. Каждый сообщает базовый commit; артефакты привязываются к проверенной версии. Прежние ветки A/B уже объединены, это не заменяет фиксацию нового рабочего diff.

## Объединение и приёмка

Порядок: готовые backend и frontend с контрактными проверками → объединение → один живой прогон агентом 3 → исправление дефектов владельцами → повтор затронутого сценария → актуализация слайдов. Конечная приёмка неизбежно общая; её нельзя заменить тремя независимыми отчётами.

Агент 3 — единственный владелец демонстрационного Docker-стенда на время репетиции. Остальные не перезапускают его. Не останавливать чужие Compose-проекты. При необходимости отдельного стенда использовать отдельные project/domain/partition/порты.

Готовность потока: пользователь задаёт достижимую точку, видит путь и движение, робот достигает её, затем возвращается и подтверждает finish; Stop останавливает физически. Презентация содержит только проверенные факты, а непроверенные функции явно обозначены.
