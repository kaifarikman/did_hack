# Контракт потока защиты D1

Статус: зафиксированное проектное задание для параллельной реализации, ещё не существующий API. Прочие поля и семантика текущего HTTP сохраняются. Версия state после расширения — `1.4`; старые 1.0–1.3 frontend продолжает читать.

## Команда

Расширить существующий `POST /api/v1/runs`, не вводить отдельного владельца движения:

```json
{
  "request_id": "unique-command-id",
  "scenario": "easy",
  "seed": 7,
  "map_mode": "static",
  "robot_count": 1,
  "task_type": "navigation",
  "navigation_target": {
    "position_x_m": 0.5,
    "position_y_m": 0.5,
    "map_id": "exact-map-id-from-api"
  }
}
```

Координаты примера иллюстративные, не гарантированно достижимая точка. `map_id` брать из `/api/v1/map`; координаты в той же системе. По умолчанию `task_type=research`, `navigation_target=null`: старый start работает как раньше. Навигационный профиль этого потока — easy/static/1. Навигация требует target, research запрещает ненулевой target. Текст миссии не заменяет координаты и не меняет обязательную цель навигации.

`GET /api/v1/health`: добавить `supported_task_types: ["research", "navigation"]` только после подключения navigation. Старый backend без поля означает только research; UI не предлагает доступный navigation вслепую.

Ответ start — 202 и текущий снимок, как раньше. До reset проверить типы, finite координаты, карту, границы, запретные/неизвестные клетки, существование пути туда/домой и конфликт активной миссии. После reset заново проверить актуальную карту, позу, наблюдения и энергию перед движением. Не обещать достижимость по проверке старого снимка.

Ошибки в существующем envelope `{error:{code,message,retryable}}`:

- 422 `invalid_request`: схема, нечисловые/нефинитные координаты, неверное сочетание полей.
- 422 `navigation_target_unreachable`: цель вне карты, запрещена или нет допустимого пути; retryable=false.
- 409 `map_changed`: map_id изменился; retryable=false, нужна новая карта/подтверждение пользователя и новый request_id.
- 409 `run_conflict`: другой активный прогон или request_id повторён с иным содержимым; retryable=false.
- 409 `scenario_unavailable`: неподдержанный профиль/режим/число роботов; retryable=false.
- 503 `environment_not_ready`: нет готовых наблюдений/карты; retryable=true.

Сохранить существующую идемпотентность: повтор того же request_id и тела не делает второй reset/start; изменение target включено в fingerprint. После неизвестного сетевого исхода UI сверяет state, не создаёт новый идентификатор автоматически.

## Снимок state 1.4

Добавить `task_type` (`research` по умолчанию) и nullable `navigation`:

```json
{
  "task_type": "navigation",
  "navigation": {
    "target": {"position_x_m": 0.5, "position_y_m": 0.5, "map_id": "map-version"},
    "phase": "moving_to_target",
    "target_reached": false,
    "target_reached_at_s": null,
    "arrival_tolerance_m": 0.12
  }
}
```

`arrival_tolerance_m` сериализуется из фактических настроек, 0.12 — пример. phase: `pending`, `moving_to_target`, `returning`, `finished`, `stopped`, `failed`. Путь, поза, батарея, freshness и last_error берутся из существующих полей; не вводить альтернативные копии. `navigation=null` для research. Для старых state frontend подставляет research/null.

После достижения: записать `target_reached=true`, время симуляции и событие `navigation_target_reached`; остановить текущий ход и перейти к возврату на базу. `completed` только после достижения цели, возвращения и подтверждённого finish. Один факт прибытия к цели не выдавать за завершение всей миссии. Judge не менять ради демо; если его реальные правила не позволяют navigation без collect, агент 1 фиксирует проблему до объявления готовности.

При недостатке бюджета до достижения: безопасный возврат имеет приоритет, цель отмечается недостигнутой, итог не completed (failed с `navigation_goal_not_reached` после безопасного возврата). Пользовательский Stop — stopped. Невозможность безопасного возврата — остановка и явная ошибка. Поздний ответ LLM не меняет цель: режим navigation детерминированный и не зависит от доступности провайдера.

JSONL использует текущую оболочку и события `navigation_target_set`, `navigation_target_reached`, `navigation_return_started` со ссылкой на run/generation, позой, целью, ревизией пути и временем. Терминальный исход — по существующему журналу миссии. UI показывает цель отдельно от текущей подцели возврата.

## Общие случаи проверки

Research без новых полей; допустимая цель; стена/вне карты/нет пути; устаревшая карта; нехватка энергии; одинаковый/конфликтующий request_id; Stop во время движения; цель достигнута и возврат ещё идёт; подтверждённый finish; потеря связи; старый state 1.3. Каждый исполнитель делает свои fixtures этого контракта в своей области файлов.
