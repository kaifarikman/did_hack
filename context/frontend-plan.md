# План улучшения фронтенда двумя агентами

Дата: 2026-10-08. **Статус:** утверждён пользователем 2026-10-08; F1 и F2 выполнены, исправления после аудита — X1 и X2 (`frontend-reports/fix-x1.md`, `fix-x2.md`).

Задача — довести панель до идеала по правилам [frontend-rules.md](frontend-rules.md) и дизайн-системе [tokens.md](tokens.md). Каждое состояние данных должно быть показано красиво, анимировано, на двух языках и проверено. Полный список состояний — в [frontend-coverage.md](frontend-coverage.md).

Ограничение: backend и HTTP-контракт `/api/v1` не меняются. Всё, что панель показывает, уже есть в `domain/contract.ts`. Новые поля — отдельная договорённость с потоком B полного решения.

## Как делим работу

Делим не по экранам, а по слоям: так два агента почти не трогают одни и те же файлы.

| Агент | Роль | Что делает |
| --- | --- | --- |
| **F1 — Система** | Фундамент, по которому строятся экраны | Инструменты и проверки, токены, глобальные стили, примитивы `shared/ui`, примитивы движения, инфраструктура i18n, чистка `domain`/`application`, единство стиля, презентация на тех же токенах |
| **F2 — Экраны** | Всё, что видит пользователь | Раскладка, фичи (миссия, карта, план и исследование, журнал, команда, язык), сценарии демо на все состояния, словари фич, анимации экранов, e2e и скриншоты |

### Ветки

Каждый агент работает в своём worktree:

- F1 — ветка `feature/frontend-system`;
- F2 — ветка `feature/frontend-screens`.

Обе стартуют от одного коммита `main`. Коммиты, слияние и PR делает пользователь. Агенты только предлагают сообщения и команды.

## Рубеж 0 — договорённости

Первая задача обоих агентов, до кода. Занимает минуты, а не часы.

1. **F1** пишет `context/frontend-contracts.md`:
   - имена семантических токенов (`--surface-*`, `--text-*`, `--action-*`, `--border-*`, `--data-*`, `--radius-*`, `--dur-*`, `--motion-*`);
   - API примитивов `shared/ui` и `shared/motion`: пропсы и варианты;
   - API i18n: `useTranslation`, `useFormatters`, `msg()`, `LocalizedError`.
2. **F2** дописывает туда:
   - раскладку `ui/features/*`;
   - список сценариев демо из [frontend-coverage.md](frontend-coverage.md);
   - какие примитивы нужны каждой фиче.
3. Оба читают и подтверждают. После этого имена и сигнатуры меняются только по согласию обоих.

## Когда фронтенд считается идеальным

Всё ниже проверяется, а не утверждается на словах:

1. `npm run verify` зелёный, ratchet-база пуста: ни одного файла длиннее 250 строк, ни одного комментария, кириллица только в словарях.
2. Каждая ячейка [frontend-coverage.md](frontend-coverage.md) имеет сценарий демо, тест и скриншот на обоих языках.
3. Каждая строка таблицы анимаций 5.3 реализована и покрыта тестом. Reduced motion проверен.
4. Тесты единства зелёные: одна роль — один компонент, шкалы только из токенов.
5. axe — 0 нарушений, контраст и цели нажатия проходят.
6. Карта держит 60 fps на проекторном разрешении.
7. Панель, презентация и экспорт используют один CSS токенов.
8. Живая проверка с настоящим backend на одном easy-прогоне. Её делает не пользователь, а владелец стека.

## Синхронизация

- **Рубеж 0:** общий документ контрактов.
- **Рубеж 1 → 2:** F1 сообщает о готовности токенов и первой волны примитивов. F2 переносит фичи.
- **Рубеж 2 → 3:** пользователь сливает обе ветки. F1 проверяет `verify` на объединённом коде, F2 — скриншоты.
- Найденный дефект возвращается владельцу файла.
- Каждый агент ведёт отчёт: `context/frontend-reports/f1.md` и `context/frontend-reports/f2.md`.
