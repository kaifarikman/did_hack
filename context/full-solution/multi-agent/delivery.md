## Как разделить разработку

Это роли исполнителей кода, отличные от трёх runtime-агентов продукта. Рекомендуемые три потока после MA-01:

- **Навигация/ROS:** NAV-01–04, физические проверки, временные препятствия. Владеет motion/navigation и транспортом датчиков.
- **Память/оркестрация:** MEM-01, AG-01–02. Владеет сборкой контекста и вызовами ролей за Planner; не меняет напрямую привод.
- **Наблюдаемость/оценка:** OBS-01, EVAL-01, React, scripts/analysis. Использует согласованную MA-01, не создаёт свою модель энергии.

Общий интегратор согласует изменения ports, HTTP и MissionController отдельными маленькими коммитами. Два потока не редактируют их одновременно. Worktree и отдельный Docker project/ROS domain/Gazebo partition/порты на поток; один владелец живого стенда во время серии. В этом обсуждении новые агенты-разработчики не запускались.

## Как доказать пользу мультиагентности

Сравнить: текущий одиночный планировщик; оркестратор с ограниченной памятью; оркестратор + исследователь; все три роли. Сначала одинаковое ограничение числа/стоимости LLM-вызовов, затем при необходимости отдельно сравнение при свободном бюджете. Иначе улучшение может объясняться просто большим вычислением.

Основные исходы: подтверждённые сборы, успешность возврата, нарушения/штрафы, длительность, энергия. Дополнительно: RMSE расхода, опасный недопрогноз, качество обнаружения изменений, ложные тревоги, фактически проверенные гипотезы, доля принятых/отклонённых планов, p50/p95 задержки и токены/стоимость.

Отдельно фиксировать причины провалов: навигация, неверное измерение, устаревший контекст, сбой инструмента, плохой план. Заморозить правила анализа до контрольной серии; тренировочные seeds используются для настройки, контрольные — только для оценки. Скрытая истина попадает исключительно в отдельный post-run анализ. При малой выборке показывать парные точки и ограничения выводов.

Если критик не улучшает исходы или обнаружение ошибок при сравнимом бюджете, вызывать его только для сложных экспериментов/разбора. Предпочтение мультиагентности сохраняется, но каждый вызов должен иметь измеримую задачу.

## Что отложить

Пока не добавлять отдельные LLM для навигации, базы данных, каждого датчика или каждого робота; второй dashboard; vector database; микросервисную сеть; автоматическое бесконечное переписывание собственных правил. Возвращаться к этим идеям только при конкретном ограничении, подтверждённом измерениями.
