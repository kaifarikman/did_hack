## A1. Сценарии и физическая модель (частично)

**Сделано и проверено тестами** (судья: 73 теста, backend: 84 пройдено, 1 пропущен):
- `generate_scenario` даёт профили easy 3/1, medium 5/3, hard 7/4 (`simulation/judge/config/local_*.json`). Размещение образцов, зон и событий — независимые потоки случайности `stream_for(seed, purpose)`; число образцов не меняет раскладку зон.
- Энергетическая разрешимость (локальное правило): путь база→образец→база по кратчайшему пути на сетке занятости не больше `max_round_trip_battery_fraction` (0.5) батареи. Невозможный сценарий отклоняется с причиной.
- `POST /reset {"seed","scenario"}` в супервизоре (неизвестный сценарий → 422); ROS-адаптер передаёт `scenario`. Reset — рестарт процессов, поэтому все воздействия снимаются.
- Hard (`dynamics.py`, `dynamic_events=true`): скрытая смена положения зоны грунта, опасная зона с `hazard_hit` и штрафом, три типа неисправности датчика образцов (пропадание, залипание, повышенный шум). Расписание не публикуется.
- Живая проверка: `docker compose -p did-a up -d simulation`, reset `seed=5 scenario=hard` → ready, судья запущен с `local_hard.json`, топики `/did/*` публикуются. Прохождение миссии с событиями в Gazebo не выполнялось.

**Не сделано:**
- Измеримое замедление грунта в Gazebo (нужен эксперимент с физикой/трением; пока грунт только повышает расход в судье).
- Независимая физическая поза Gazebo вместо odom судьи, проверка collect/finish/коллизий по ней.
- Проверка утечек истины в образах/mounts. Замечание: `./simulation` целиком монтируется в backend-сервис только через `judge/data`, но конфиги профилей лежат в `judge/config` — отдельный аудит ещё нужен.
- Публичные поля наблюдений для событий hard (`hazard_hit` уже идёт в `/did/events`; пропадание датчика для B выглядит как отсутствие сообщений — контракт с B не согласован).

**Не начато (на момент первой записи):** A3 SLAM, A4 два робота, A5 финальный выпуск и скилл `ros-check`. Это многодневный объём с Gazebo-экспериментами и рубежами совместно с B.

## A3. SLAM (частично)

- Профиль `map_mode=slam` (SLAM Toolbox 2.8.5, `simulation/config/slam_params.yaml`); готовая карта в SLAM не передаётся. Система координат: кадр `map` начинается в точке старта, мир = база + map-поза (правило и ограничения — `simulation/README.md`).
- Проба на одном роботе: ошибка позы SLAM против физической позы Gazebo 0.011 м в среднем, 0.027 м максимум, карта 4412 известных клеток (`simulation/artifacts/a3-slam-probe.log`).
- Адаптер backend `RosSlamMapSource` (`backend/src/adapters/ros/slam_map.py`, 4 теста) превращает `/map` или `/team/map` в `OccupancyGrid` контракта; `map_mode` пробрасывается в reset. **Не сделано:** подключение адаптера в точке запуска backend (`entrypoint`, файл B), передача качества позы и версии карты в публичные поля (контракт F02 с B), поведение при loop closure на длинном маршруте, рубеж 2 с B.

## A4. Два робота (частично)

- Два Burger в одном мире (`multi_robot_world.launch.py`, `scripts/robot_model.py`): раздельные топики, кадры, TF-префикс, мосты, страж скорости на каждого. Проба независимости: `simulation/artifacts/a4-two-robots-probe.log` (едет только `robot_1`: 0.594 м, `robot_2`: 0.000 м).
- Командный судья `TeamJudge` + `team_node`: общие образцы с единственным зачётом (в т. ч. при параллельных потоках — тест), раздельные батарея, коллизии, finish; `/did/team_score` перечисляет результаты каждого робота и `failed_robots`. 15 тестов судьи на командный режим и модель.
- Проба в Gazebo (`a4-team-probe.log`): адресность команд, независимость батарей, остановка робота при потере команд без влияния на второго, регистрация столкновения, раздельный штраф ложного сбора.
- Командный SLAM: два экземпляра + слияние в `/team/map` (мировые координаты). Ошибка локализации обоих 0.013 м в среднем; совпадение занятых клеток с эталоном 0.979 (`a4-team-slam-probe.log`). Во время отладки найдены и исправлены три дефекта запуска: параметры SLAM не применялись к namespaced-узлам (ключ `/**`), оба SLAM писали в абсолютный `/map`, проверка готовности supervisor требовала успеха всех топиков в одной итерации.
- **Не сделано:** сбор реального образца двумя роботами одновременно в Gazebo, встречное движение с разъездом, полная командная миссия с возвратом обоих, рубеж 3 с координатором B (нужны координатор и UI команды).

## Запуск режимов и командная миссия

- `scripts/stack.py up --robots 1|2 --map static|slam --scenario … --seed …` поднимает simulation и делает reset в любой из четырёх режимов (проверен 2 робота + SLAM + hard); `down` останавливает. Backend/панель — отдельной командой Compose; профиль режима в самом backend (`MAP_MODE`, `robots`) не подключён (файлы B).
- Командная миссия в Gazebo (`simulation/artifacts/a4-team-collect-probe.log`): два робота к одному образцу, один зачёт, оба вернулись и завершили успешно, коллизий нет.
- Остаётся: параллельный collect в один тик в Gazebo, встречный разъезд с препятствиями, рубежи 1–3 с B, полная серия, итог.

## A2. Первый прогон medium (диагностический, не рубеж)

Полный стек, `scenario=medium`, seed 1, LLM выключена (fallback-планировщик), backend с локально расширенным `SUPPORTED_SCENARIOS` (правка в файле B откатана, не закоммичена). Результат (`artifacts/evaluation/a2-medium-first/`): статус `failed`, 0 образцов, батарея 4.4 из 60, 293 с; робот вернулся на базу и остановился (`robot_stationary=true`), `last_error=no_confirmed_sample`. Журнал: к концу прогона все цели `approach` отклонялись исполнителем из-за нехватки энергии. Среда и судья отработали корректно; **дефект передаётся B**: стратегия, настроенная на easy (3 образца, 1 зона), на medium (5/3 + замедление грунта) расходует батарею на поиск и не находит образец. Backend также принимает только `scenario=easy` (`run_service.py`, B). Живая LLM и hard в этом прогоне не проверялись, одного seed недостаточно для выводов.

### Дополнение: замедление, физическая поза, стенд

- **Замедление грунта** — решение и контрольный проезд в `simulation/README.md` (0.275 м в зоне против 0.548 м вне, отношение 0.501); лог `simulation/artifacts/a1-soil-slowdown-probe.log`. Замедление программное (страж скорости), не трение Gazebo.
- **Физическая поза:** судья подписывается на `/world/default/pose/info` через gz-transport внутри процесса (сущность `burger`), в ROS поза не публикуется; `pose_source=odom` — явный запасной вариант. Живая проверка: проезд 0.545 м по odom → расход 0.541, ошибок отката в логе нет. Collect/finish/повороты используют эту позу; коллизии пока определяются по лидару (`/scan`, порог 0.14 м), независимой проверки контактов Gazebo нет — пункт остаётся частичным.
- **Стенд `scripts/evaluation/`** (A2, частично): серия с таймаутом и остановкой, полный журнал, сохранение неудач и start_rejected, проверка неподвижности по двум снимкам позы, манифест (commit, dirty, хеши конфигов), раздельные наборы seed tuning/control (`seeds.json`), 5 тестов. Живая серия не запускалась: backend принимает только `scenario=easy`, поддержка medium/hard — за B.
