# Пул задач MVP: два агента

Подготовлен 2026-10-06 по запросу пользователя. Это первоначальная декомпозиция MVP; реализация уже ведётся, свидетельства готовности находятся в задачах и общем контексте. Допущения о локальном судье не являются правилами организаторов.

**Цель расширена пользователем:** весь кейс и все бонусы описаны в [плане полного решения](../full-solution/README.md). Этот документ сохраняет критерии первого рубежа. Исключённые из MVP функции обязательны на следующих этапах полного плана.

## Результат MVP

Одна команда поднимает симуляцию и панель. Пользователь запускает easy; робот сам находит и собирает минимум один образец по шумному датчику, возвращается с положительной батареей и получает подтверждение судьи. На панели видны положение, путь, заряд, подцель и журнал исследования. LLM задаёт подцели; ошибки модели обрабатываются алгоритмическим резервным планом.

Включаем базовую оценку грунта и одну проверенную по измерениям гипотезу. Hard, полноценная адаптация к внезапным изменениям, SLAM и второй робот — следующий этап. Генератор MVP создаёт только easy; medium и hard из полного ТЗ остаются в дальнейшем плане.

## Два потока

| Исполнитель | Что получает на вход | Что сдаёт | Задание |
| --- | --- | --- | --- |
| A — backend, робот и среда | ТЗ, ROS-контракт, HTTP-контракт | Docker/Gazebo, судья, автономная миссия, LLM, журнал, HTTP и общий запуск | [backend.md](backend.md) |
| B — frontend и демонстрация | HTTP-контракт и синтетические примеры | Панель миссии, карта, журнал, управление стартом/остановкой, независимый Dockerfile | [frontend.md](frontend.md) |

Это независимость разработки, а не отсутствие интеграции. A проверяет робототехнику без браузера; B делает интерфейс без ROS и работающего backend. Последняя проверка связывает обе реализации. Поток A тяжелее и определяет срок готовности MVP; интерфейс не должен задерживать первый успешный автономный прогон.

## Порядок работы

1. Оба агента читают `AGENTS.md`, этот файл, архитектуру, контракт и своё задание. Работают в принадлежащих им путях.
2. A первым проверяет запуск Gazebo на ARM64; B одновременно запускает UI на fixture-адаптере. При проблемах графики A отдельно проверяет сервер симуляции и способ демонстрации; совместимость не считается доказанной до прогона.
3. A поднимает HTTP со снимками реальных наблюдений; B подключает live-адаптер без изменения модели представления.
4. A владеет общим Compose и сквозной приёмкой. B исправляет frontend по результатам интеграции. Общие изменения контракта координируются, а не расходятся на две версии.
5. Каждый агент отмечает свои задачи выполненными только с проверяемым свидетельством: команда, результат теста или путь к логу. Финальный ответ перечисляет готовое, ограничения и точные команды запуска.

Публикация, push и создание PR в этот пул не входят. Названия каталогов и команды в задачах являются целевой структурой, пока соответствующие файлы не реализованы.

## Общая приёмка

- [ ] **MVP-01 — запуск.** Из документированной конфигурации Docker Compose собирает стек; доступны панель, Gazebo и ROS. Инструкции указывают проверенную платформу и реальный способ отображения симуляции.
- [ ] **MVP-02 — реальная миссия.** На фиксированном easy seed робот по `/did/sample_sensor` находит и подтверждённо собирает минимум один образец, возвращается и успешно вызывает `/did/finish`; батарея положительная. Скрытая конфигурация не используется планировщиком.
- [ ] **MVP-03 — воспроизводимость.** Два последовательных старта одного seed корректно сбрасывают мир, батарею, образцы, модель и журнал; оба завершаются успешно. Это минимальная проверка повторяемости, не статистическое доказательство качества.
- [ ] **MVP-04 — LLM.** При настроенном API выполнена хотя бы одна реальная подцель модели; запись содержит её обоснование. При таймауте или невалидном ответе робот остаётся под контролем, а fallback виден в панели и журнале. Без ключа этот пункт остаётся частично непроверенным.
- [ ] **MVP-05 — исследование.** Хотя бы одна гипотеза о стоимости грунта связана с измерениями, действием, сравнением ожидания с результатом и выводом. Оценка участвует в планировании пути или запаса возврата. Заранее написанный текст без измерений не засчитывается.
- [ ] **MVP-06 — остановка и сбои.** Stop останавливает исполнение без ложного успеха; устаревшая телеметрия останавливает робот независимо от HTTP/LLM; потеря связи UI сохраняет последние данные с видимой отметкой.
- [ ] **MVP-07 — интерфейс.** Карта и поза совпадают в мировых координатах, видны батарея, сигнал, сборы, цель, путь, режимы планировщика/судьи и журнал. Экспорт включает все страницы журнала выбранного прогона.
- [ ] **MVP-08 — тесты и границы.** Проверены предметные правила без ROS, HTTP-контракт, fixture/live-адаптеры UI и интеграция с Gazebo. В импортах соблюдено направление зависимостей; ключи отсутствуют в UI и логах.

Свидетельства сквозного прогона агент A сохраняет в своей документации с seed, конфигурацией судьи, командами, результатом и ссылкой на журнал. Отдельно отмечает local/official и наличие настоящего LLM. Панель с демо-данными не заменяет ни один пункт физической приёмки.

## Что известно и что принято для начала

Docker выбран пользователем. Чистая архитектура и работа двух агентов явно запрошены. Python/FastAPI, TypeScript/React и HTTP polling — рабочий выбор для данного плана, а не ограничение ТЗ.

До ответа организаторов выполняется локальный судья с настраиваемыми предположениями. Базу для него принимаем равной точке старта. LLM настроена, реальный вызов планировщика проверен; это не заменяет приёмку целой миссии. Подробности в [environment.md](../environment.md).
