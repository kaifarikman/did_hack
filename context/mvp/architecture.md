# Архитектура MVP

Рабочий проект решения от 2026-10-06 в рамках запроса пользователя: подготовить MVP для двух независимых агентов и соблюдать чистую архитектуру. Это решения для реализации, а не дополнительные требования организаторов.

## Объём

Один TurtleBot3 Burger, готовая карта, easy (3 образца, 1 грунтовая зона). Успех минимальной миссии: самостоятельно найти по датчику и собрать хотя бы один образец, вернуться на базу с положительным остатком батареи, получить подтверждение завершения от судьи. UI показывает фактическую миссию и объяснения. LLM выбирает проверяемые подцели; алгоритмический резервный план позволяет продолжить при ошибках модели.

В MVP включены базовая оценка стоимости грунта и журнал проверяемой гипотезы. Полный hard, смена грунтов во время прогона, отказы датчика, SLAM, второй робот и оптимизация максимального счёта идут после MVP. Успешный MVP не означает выполнение всех уровней ТЗ.

## Рабочий стек

- Backend: Python, чистая предметная логика, ROS 2 адаптеры и небольшой HTTP-адаптер на FastAPI.
- Frontend: TypeScript, React, Vite; карта через Canvas или SVG, без отдельного картографического сервиса.
- Запуск: Docker Compose; ROS 2 Jazzy, Gazebo Harmonic и TurtleBot3 — версии из ТЗ. Агент A проверяет совместимость пакетов с ARM64 и фиксирует реально работающие версии.
- Хранение MVP: файлы журнала JSONL и конфигурации сценария; отдельная БД не нужна.
- Между frontend и backend: HTTP JSON с опросом состояния. Контракт в [interface.md](interface.md); браузер напрямую с ROS не работает.

Версии Python/Node и библиотек выбираются при сборке и фиксируются lock-файлами. Их совместимость пока не проверена.

## Направление зависимостей

```text
backend:   ROS / HTTP / LLM / файлы → application → domain
frontend:  React / HTTP / fixtures → application → domain
```

`domain` содержит правила и значения; `application` координирует сценарии через порты; адаптеры реализуют работу с внешним миром. Сборка зависимостей происходит в точке запуска. Ядро не импортирует ROS, FastAPI, HTTP-клиент, React, браузерные API или файловую систему.

Не нужен интерфейс для каждого класса. Порты вводятся там, где есть реальные альтернативы: ROS и тестовый робот, HTTP и тестовый источник UI, LLM и алгоритмический планировщик, файловый и тестовый журнал. Состояние миссии и переходы принадлежат backend; frontend отображает их и отправляет намерения пользователя.

## Структура и владение

| Путь будущей реализации | Владелец | Содержание |
| --- | --- | --- |
| `backend/src/domain/` | A | Миссия, подцели, запас возврата, оценка грунта |
| `backend/src/application/` | A | Исполнение миссии, координация наблюдений и планирования, порты |
| `backend/src/adapters/` | A | ROS, HTTP, LLM, сохранение журнала |
| `backend/tests/` | A | Тесты ядра, контрактов и интеграции |
| `simulation/` | A | Судья, генератор easy, настройки ROS и launch |
| `infra/`, `compose.yaml`, корневые скрипты запуска | A | Сборка и интеграция стека |
| `frontend/src/domain/` | B | Модель представления миссии и правила отображения |
| `frontend/src/application/` | B | Загрузка состояния, команды, координация обновлений |
| `frontend/src/adapters/` | B | HTTP и fixture-источник с одинаковым интерфейсом |
| `frontend/src/ui/` | B | Карта, панель миссии, журнал, состояния ошибок |
| `frontend/tests/`, `frontend/Dockerfile`, `frontend/README.md` | B | Проверки и независимый запуск frontend |
| `context/mvp/interface.md`, `context/mvp/examples/` | Координатор | Общий контракт и согласованные примеры |
| `context/mvp/backend.md` | A | Задачи и результаты backend |
| `context/mvp/frontend.md` | B | Задачи и результаты frontend |

Агенты изменяют свои пути. Агент A интегрирует frontend в Compose через его Dockerfile и документированный запуск. Общий контракт меняется через координатора с обновлением обеих сторон и примеров. Все перечисленные пути к коду — план, а не уже существующие модули.

## Границы знаний и ответственности

- Судья владеет истинным расположением образцов, параметрами грунта и правилами расхода. Алгоритм агента получает только разрешённые наблюдения.
- Пока официальный судья не получен, агент A реализует локального судью с явной маркировкой `local`. Его формулы — допущения проекта; совместимость с неизвестными правилами организаторов не заявляется.
- Для локального easy база совпадает со стартом, расход, шум и допуск возврата заданы конфигурацией. Перед подключением официального судьи эти предположения сверяются заново.
- Планировщик LLM возвращает намерения, но не скорости. Исполнитель проверяет достижимость, запас батареи и допустимость действия.
- HTTP и UI не управляют `/cmd_vel`. Остановка миссии проходит через исполнитель; аварийная остановка при устаревших наблюдениях работает без браузера и LLM.
- Официальный успех устанавливается по ответу судьи на завершение. Кнопка Stop означает прерывание, а не успешное возвращение.
- Секрет LLM доступен только backend через окружение; журнал и браузер его не получают.

## Проверки архитектуры

Ядро backend тестируется без ROS/Gazebo и сети. Frontend проверяется с fixture-адаптером без backend. Одинаковые контрактные примеры используются обеими сторонами. Финальная приёмка обязательно проходит в Gazebo с настоящими ROS-сообщениями; fixture-демо не доказывает работоспособность робота.
